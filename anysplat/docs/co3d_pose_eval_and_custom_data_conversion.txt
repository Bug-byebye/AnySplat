================================================================================
  CO3D 式位姿评测：自定义数据转换说明 + 评测流程说明
  （适用于本仓库 eval_pose.py / eval_pose_vggt.py 与
   scripts/convert_material_sweep_for_anysplat_eval.py）
================================================================================

一、文档目的
------------
本文用说明性文字概括两件事：（1）如何将自有场景数据整理成与 CO3D 位姿
评测脚本兼容的目录与标注格式；（2）评测脚本如何读入数据、如何采样、
如何计算指标。便于论文方法/实验设置撰写或组内交接，不涉及逐行代码导读。


二、端到端在做什么
------------------
整体可以看成两段串联的流水线。

第一段是「数据准备」。若你已有的是 NeRF 类场景（每个场景一份
transforms.json 与 rgb 图像目录），可通过本仓库提供的转换脚本，生成
「图像树」与「gzip 压缩的 JSON 标注」，其组织方式刻意模仿官方 CO3D
评测所用的文件名与字段，从而使得第二段无需改评测代码即可运行。

第二段是「位姿评测」。评测程序把每个类别下的测试标注读进来，按序列
（在自建数据里通常对应一个场景文件夹名）遍历；在每个序列中抽取固定
数量的视角，用模型估计相机外参，再与标注中的真值外参做相对位姿意义
上的比较，最后在多个角度阈值上汇总成 AUC，并在类别间做平均。


三、转换脚本的角色与位置
------------------------
脚本路径：scripts/convert_material_sweep_for_anysplat_eval.py

它面向的典型输入，是磁盘上若干「场景目录」。每个场景目录内需包含
transforms.json（内含 frames 列表，每帧有 transform_matrix 与图像路径
信息），且同目录下存在 rgb 子目录存放图像。脚本会在输入根目录下递归
查找满足条件的场景。

转换完成后，在指定的输出根目录下会生成多块内容，彼此分工如下。

（1）pose_co3d：位姿评测真正要读的「图像根」。其下按「类别名」再按
    「序列名（场景名）」分子目录，里面是重命名后的帧图像（如六位数字
    编号加后缀）。评测时参数 --co3d_dir 应指向这一层的父路径，即
    pose_co3d 本身。

（2）pose_annotations：存放若干 gzip 压缩的 JSON 文件，文件名形如
    「某类别_test.jgz」。评测时参数 --co3d_anno_dir 指向该目录；若使用
    --categories auto，则脚本会扫描目录下所有匹配 *_test.jgz 的文件名，
    从中解析出类别名。

（3）nvs_scenes：为另一类评测（新视角合成等）准备的图像副本，与位姿
    评测逻辑独立；若你只关心位姿指标，可只关注 pose_co3d 与
    pose_annotations。

此外还会写出 nvs_scene_index.json、conversion_meta.json 以及一份带示例
命令的 README_evaldataset_anysplat.json，便于复现转换参数与回忆如何调用
评测脚本。

关于「类别」如何产生：若场景目录名中含有双下划线「__」，则取最后一个
「__」右侧的子串作为类别名（便于把材质、物体类型等编码进场景名）；否则
归入「uncategorized」一类。每一类对应一个独立的 *_test.jgz，因此类别
在文件系统层面是分文件的。


四、标注文件里每一条记录表示什么
--------------------------------
每个 *_test.jgz 解压后是一个大 JSON 对象：键为序列名（场景名），值为
该序列中所有参与评测的帧的列表。

列表中每一帧是一个小对象，包含三个键。

filepath：相对「图像根」（即 --co3d_dir）的路径字符串。评测脚本会把
co3d_dir 与 filepath 拼接得到磁盘上的绝对路径，再读图。因此 filepath
必须与 pose_co3d 下的实际相对路径一致。

R 与 T：表示该帧相机外参在「PyTorch3D / CO3D 标注侧常用」的旋转与平移
约定下给出的量，而不是直接写成 OpenCV 外参矩阵。转换脚本从
transforms.json 中的 4x4 矩阵出发，先按用户选项得到世界到相机的 OpenCV
意义下的外参，再经互逆映射写入 R、T，使得评测代码里已有的
convert_pt3d_RT_to_opencv 能还原回与图像渲染一致的 OpenCV 外参。若你
绕过本脚本自建标注，必须保证与这一互逆关系一致，否则真值与图像不对齐，
指标将失去意义。

转换脚本还支持若干与坐标系相关的选项，例如 transform_matrix 解释为
相机到世界还是世界到相机（c2w / w2c），以及是否对 Blender/OpenGL 风格
相机轴做固定对角阵修正。这些选项会改变写进 R、T 的数值，应与你的数据
来源约定一致后再固定写进论文或附录。


五、从转换结果接到评测命令
--------------------------
位姿评测至少需要两个路径参数。

--co3d_dir：指向转换输出中的 pose_co3d 目录。

--co3d_anno_dir：指向转换输出中的 pose_annotations 目录。

类别可使用 --categories auto，与官方 CO3D 习惯一致。

需要特别注意的一个默认值：eval_pose.py 中 min_num_images 默认较大（50），
而转换脚本默认只要求每个场景不少于 10 帧即可保留。若你不改评测侧参数，
大量自建序列会因「帧数不足」被整条跳过。实践中应把 --min_num_images 设成
与转换时采用的最小帧门槛一致（或与真实帧数匹配），否则会出现「转换成功
但评测几乎无有效序列」的现象。

另一个与数据相关的门槛在评测内部：在随机（或计划固定的）若干索引上
取图后，若首张被采样图像的最大边长小于 448 像素，该次采样结果会被丢弃。
若转换时对图像做了过强的缩小，可能导致有效评测样本变少。

多模型公平对比时，更推荐使用 eval_pose_vggt.py：它会先为所有序列生成
统一的视角采样计划并落盘，再对各模型复用同一批帧索引，避免「不同模型
看到不同子集」带来的额外方差。单模型快速复现仍可使用 eval_pose.py。


六、评测阶段如何理解「采样」
----------------------------
对每个序列，评测先从标注列表构造元数据（图像路径与由 R、T 还原的外参）。
若序列长度小于 min_num_images，则整条序列不参与评测。

接着会过滤明显异常的平移（实现上若三个分量之和过大则丢弃整条序列）。

随后在序列内无放回地抽取 num_frames 个索引（默认 10），对应 num_frames
张图与其外参。若未使用统一采样计划，则随机性由随机数种子控制；若使用
eval_pose_vggt 生成的计划，则这些索引在多次运行与多模型间保持一致。

读取图像后，还会检查分辨率门槛（首张采样图 max 边长是否达到 448）。
未通过则该序列本次不产生误差样本；注意随机数状态仍可能已前进，这与
「先采样再判失败」的实现顺序有关。

图像经 load_and_preprocess_images 等与训练一致的预处理后送入网络。AnySplat
路径通过编码器与相机头得到位姿编码，再解码为外参与内参；位姿误差只依赖
外参部分。VGGT 路径为整网前向得到位姿编码后用同一套解码函数得到外参。
可选的 bundle 调整分支仅存在于 AnySplat 路径，与自建数据是否启用取决于
命令行开关。


七、真值与预测如何对齐到同一规范
--------------------------------
外参先升为 4x4 齐次形式。默认策略（legacy / gt_only）是：仅对真值相机轨迹
做「以第一帧相机为参考系」的右乘逆变换，消去整体刚体自由度的一种常见
取法；预测外参在默认设置下不再额外对齐。可选策略可对预测与真值都相对
第一帧对齐，用于消融或对齐假设不同的实验，详见 eval_pose_vggt 的
pose_postprocess 选项说明。

在此之后，在所有帧对之间构造相对位姿，分别比较相对旋转与相对平移方向
的角误差（单位为度），并对平移方向误差的 180 度歧义做处理。每一对帧
产生一对旋转误差与平移误差；后续 AUC 在每一对上会取二者逐对的最大值
作为该对的标量误差代表。


八、AUC 指标如何汇总
--------------------
对每个角度阈值（实现中为 5、10、20、30 度），将所有序列、所有帧对展平
后的标量误差做成直方图并归一化，再对累积分布取平均，得到该阈值下的
AUC。每个类别单独算一套 AUC；跨类别的「平均 AUC」是对各类别 AUC 再取
算术平均（宏平均），而不是把所有帧对混在一起再算一次。

eval_pose_vggt 还会把各后端结果与命令参数写入 JSON 与可读摘要文本，
便于归档与制表；eval_pose.py 则主要写一份带时间戳的文本结果。


九、与官方 CO3D 的关系（说明性表述）
------------------------------------
本仓库评测代码最初面向官方 CO3D 测试划分与目录布局编写。转换脚本的输出
在「文件名模式（*_test.jgz）」「标注字段（filepath、R、T）」「图像根 +
相对 filepath 拼接」这几件事上与该假设对齐，因此同一套 eval_pose 系列
脚本既可用于官方数据，也可用于按该脚本整理后的自建数据。自建数据在
论文中应如实描述数据来源、坐标约定、最小帧数与分辨率处理，避免读者误
认为与官方 CO3D 子集完全一致。


十、快速核对清单
----------------
□ 转换输出的 pose_co3d 与 pose_annotations 路径是否分别对应 --co3d_dir
  与 --co3d_anno_dir。
□ --min_num_images 是否与转换时保留场景的最小帧数一致或更严。
□ transforms 的 c2w/w2c 与是否做 OpenGL 到 OpenCV 轴修正是否与数据管线
  约定一致。
□ 多模型对比是否使用统一采样计划（eval_pose_vggt + 生成的 json）。
□ 论文中是否区分「官方 CO3D」与「自建 CO3D 格式数据」。
